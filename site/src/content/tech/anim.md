# ばねとアニメーションの中核

<p class="file">対象: anim/anim.odin(192 行)/ src/anim.zig(126 行)/ src/pure_tests.zig</p>

ame-shell のすべての動きは、`ame_spring_step` という 1 つの関数で計算しています。窓・パネル・通知・歌詞・トーンアーム・壁紙の切り替え・WebAssembly のウィジェットまで、同じ関数です。[アニメーション](#/animation)のページのデモは、この関数そのものをブラウザで動かしています。

## データ: 5 つの数 {#struct}

```odin
// Zig 側の `extern struct Spring` とレイアウトを一致させること。
Spring :: struct {
	x:        f32, // 現在値
	v:        f32, // 速度(単位/秒)
	target:   f32, // 目標値
	response: f32, // 応答時間(秒)。小さいほど速い。≒ 1周期の長さ
	damping:  f32, // 減衰比 ζ。1 = 臨界減衰(行き過ぎない)、<1 = 弾む
}
```

Zig 側は同じ並びの `extern struct` として持ち、ポインタをそのまま Odin に渡します(コピーしない)。WebAssembly のウィジェットも同じ並びです。

### なぜ「応答時間」と「減衰比」か {#params}

ばねの物理は本来「質量・ばね定数・減衰係数」で書きますが、この 3 つから見た目の動きを想像するのは難しいです。そこで、**見た目に直結する 2 つ**で指定します。

- **応答時間(response)**: 1 回揺れる周期の長さ(秒)。「どのくらいの速さで着くか」。
- **減衰比(damping、ζ)**: 1 なら行き過ぎずに止まる、1 未満なら弾む、1 より大きいとゆっくり近づく。

内部では `ω = 2π / response`、`k = ω²`、`c = 2ζω`(質量 1)に換算します。iOS / SwiftUI のばね(`response` と `dampingFraction`)と同じ考え方です。

ame-shell の主な値:

| どこ | 応答時間 | 減衰比 | 狙い |
|---|---|---|---|
| 窓の位置 `px` `py` | 0.36 秒 | 0.80 | わずかに行き過ぎて止まる |
| 窓の大きさ `cw` `ch` | 0.30 秒 | 0.90 | 大きさはほぼ行き過ぎない(中身の描き直しが目立たないように) |
| 窓が開く `reveal` | 0.30 秒 | 0.68 | はっきり弾む「ポップ」 |
| 窓を閉じる | 0.18 秒 | — | 閉じるときは速く |
| ワークスペースの切り替え `slide` | 0.42 秒 | 0.92 | 落ち着いた横移動 |
| 歌詞のポップ | 0.38 秒 | 0.55 | よく弾む |
| トーンアーム | 0.60 秒 | 0.85 | 重さのある、ゆっくりした動き |
| 壁紙の切り替え | 1.6 秒 | 1.0 | 行き過ぎない、ゆったりした広がり |

## 計算: 半陰的オイラー法、1 ms の刻み {#integrate}

```odin
@(export, link_name = "ame_spring_step")
spring_step :: proc "c" (s: ^Spring, dt: f32) -> b32 {
	if s.response <= 0 {
		s.x = s.target
		s.v = 0
		return false
	}
	// k = ω², c = 2ζω(質量1)。ω = 2π / response。
	omega := f32(6.2831853) / s.response
	k := omega * omega
	c := 2 * s.damping * omega

	// フレーム落ちで dt が巨大になっても破綻しないよう上限を設ける。
	remaining := dt
	if remaining > 0.1 {remaining = 0.1}
	for remaining > 0 {
		h := remaining
		if h > MAX_STEP {h = MAX_STEP}
		a := -k * (s.x - s.target) - c * s.v
		s.v += a * h
		s.x += s.v * h
		remaining -= h
	}

	dx := s.x - s.target
	if dx < 0 {dx = -dx}
	av := s.v
	if av < 0 {av = -av}
	if dx < EPS_X && av < EPS_V {
		s.x = s.target
		s.v = 0
		return false
	}
	return true
}
```

### なぜ解析解ではなく数値積分か {#why-numeric}

減衰のあるばねには、式で答えを出す方法(解析解)があります。それを採らなかった理由は 2 つです。

1. **場合分けが要る**: 減衰比が 1 未満・1・1 より大きいで、式の形(sin / cos / exp の組み合わせ)が変わります。
2. **libm が要る**: `sin`・`cos`・`exp` を使うと、WebAssembly の freestanding(標準ライブラリの無い環境)では記号が解決できません。ame-shell の Odin は**四則演算だけ**で書く決まりにしています([言語](#/tech-lang))。

数値積分なら、同じ 10 行が、減衰比がいくつでも、ネイティブでも wasm でも同じように動きます。

### なぜ「半陰的」オイラーか {#symplectic}

`v += a·h` の後に、**更新後の v で** `x += v·h` とします(陽的オイラーは古い v で x を更新する)。この順番だけの違いで、ばねのような振動する系での**エネルギーの増え方**が大きく変わります。陽的オイラーは刻みが粗いと振動が少しずつ大きくなって発散しますが、半陰的オイラーはエネルギーが保たれやすく(シンプレクティック)、発散しません。

### なぜ 1 ms で刻むか {#substep}

```odin
// 積分の最大刻み。semi-implicit Euler は h·ω が小さければ安定する。
// response=0.08s (ω≈78) でも h=1ms なら h·ω≈0.08 で十分安定。
MAX_STEP :: f32(0.001)
```

フレームの間隔(16.6 ms や 8.3 ms)で 1 回だけ計算すると、速いばね(応答時間が短い)ほど誤差が大きくなり、**画面のリフレッシュレートによって動きが変わります**。1 ms ごとに刻めば、60 Hz なら 1 フレーム 17 回、120 Hz なら 8 回のループになり、**どちらでも同じ軌跡**になります。1 回のループは掛け算と足し算が数回なので、計算量は無視できます。

| 方法 | 正確さ | フレームレートの影響 | libm | 判断 |
|---|---|---|---|---|
| **半陰的オイラー + 1 ms の刻み** | 十分 | ほぼ無し | 不要 | ✓ 採用 |
| 解析解 | 正確 | 無し | 必要 | wasm で使えない、場合分け |
| RK4(ルンゲ=クッタ) | 高い | 少ない | 不要 | 1 刻み 4 回の評価。この用途では精度が過剰 |
| フレームごとに 1 回のオイラー | 低い | 大きい | 不要 | 120 Hz と 60 Hz で動きが変わる。速いばねで発散 |

### 長い休止と止まる判定 {#limits}

- **`dt` の上限 0.1 秒**: 画面が止まっていた後の最初のフレームで、`dt = 5 秒` を積分すると一瞬で終わってしまいます。上限で、少なくとも動きは見えるようにします。
- **止まる判定**(ずれ 0.005 未満・速度 0.01/秒 未満): UI の単位はピクセルなので、0.005 px のずれは見えません。判定に入ったら**目標にぴったり合わせて** `false` を返します。呼んだ側はこれを見て「次のフレームを頼まない」ので、[待機時の負荷が 0](#/tech-wayland) になります。

## 途中で行き先が変わっても速度を保つ {#retarget}

```zig
// src/anim.zig
/// 目標を変える。現在の位置と速度はそのまま(速度連続)。
pub fn set(self: *Spring, t: f32) void {
    self.target = t;
}
/// アニメーションせずに即座に値を置く(初回表示などに使う)。
pub fn snap(self: *Spring, t: f32) void { … }
/// 少し勢いを足す(クリック時の「ぷにっ」とした反応用)。
pub fn kick(self: *Spring, dv: f32) void { self.v += dv; }
```

`set` は**目標だけ**を変えます。位置と速度はそのままなので、動いている途中に行き先が変わっても、**勢いを保ったまま新しい目標へ曲がって**いきます。時間と曲線で動かす方法(イージング)では、途中で行き先が変わると「今の位置から、新しい曲線を 0 秒目から」始めるしかなく、速度がその瞬間に飛びます。

この性質は**テストで保証**しています。

```zig
// src/pure_tests.zig
test "spring converges and is velocity-continuous" {
    var s = anim.Spring.init(0, 0.3, 0.8);
    s.set(100);
    var t: f32 = 0;
    while (t < 0.1) : (t += 1.0 / 60.0) _ = s.step(1.0 / 60.0);
    const v_before = s.v;
    try std.testing.expect(v_before > 0);
    // 途中で目標を変えても速度は保たれる
    s.set(-50);
    try std.testing.expectEqual(v_before, s.v);
    var frames: usize = 0;
    while (s.step(1.0 / 60.0)) frames += 1;
    try std.testing.expectEqual(@as(f32, -50), s.x);
    try std.testing.expect(frames < 200);
}
```

## アニメーションの速さを全体で変える {#speed}

```zig
/// 設定の anim-speed。>1 で速く。dt に掛ける(応答時間を短くするのと等価)。
pub var speed_scale: f32 = 1.0;
pub fn step(self: *Spring, dt: f32) bool {
    return ame_spring_step(self, dt * speed_scale) != 0;
}
```

`theme { anim-speed 1.5 }` にすると、すべてのばねの時間が 1.5 倍速く進みます。すべての動きが同じ関数を通っているので、**1 か所で全体の速さを変えられます**。

### あいまい検索 `ame_fuzzy_score` {#fuzzy}

```odin
// fzf 系の考え方を簡略化: パターンの各文字が順に(飛び飛びでも)現れれば一致。
// スコアは「連続一致」「単語の先頭」「文字列の先頭」を加点し、間の飛びを減点。
// UTF-8 はバイト単位で比較する(マルチバイト文字は完全一致でのみ当たる)ので、
// 日本語名も部分一致で検索できる。ASCII のみ大文字小文字を無視。
```

| 加点・減点 | 値 |
|---|---|
| 一致した文字 | +10 |
| 文字列の先頭 | +30 |
| 区切り(空白 `-` `_` `.` `/`)の直後 | +20 |
| camelCase の境目 | +15 |
| 直前の文字も一致(連続) | +18 |
| 前の一致からの飛び | −(飛んだ文字数、最大 8) |
| 最初の一致の位置 | −(位置、最大 20) |
| 文字列の長さ | −(長さ / 6、最大 10) |

前から貪欲に 1 回なめるだけ(O(n))なので、ランチャーの全アプリに毎キー入力で掛けても時間はかかりません。テストでは「`fi` は Profile より Firefox が上」「`ターミ` でターミナルに当たる」ことを確かめています。[デモ](#/shell)

### 主色抽出 `ame_dominant_color` {#dominant}

RGB の各チャンネルの上位 4 bit で 4096 区画に分け、区画ごとに「個数と RGB の合計」を数えます。「個数 × (0.15 + 彩度²) × 明るさの減点」が最大の区画の**平均色**を返します。作業用のメモリ(4096 × 4 個の u32 = 64 KB)は呼ぶ側が渡すので、Odin の中でメモリを確保しません(`-default-to-nil-allocator` でも動く)。使い方は [ガラス・壁紙・配色](#/tech-glass)。
