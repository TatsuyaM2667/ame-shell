# 文字の描画

<p class="file">対象: src/text.zig(363 行)/ gfx.zig の文字のシェーダ</p>

```
fontconfig(書体を選ぶ) → HarfBuzz(並べる) → FreeType(輪郭を画像に) → SDF(距離場に変換) → 2048² のアトラス 1 枚 → シェーダ
```

ツールキットを使わないので、文字の描画も自分で組み立てています。日本語(漢字・かな)・英数字・Nerd Font のアイコン・絵文字が 1 行の中に混ざっても正しく並び、どの大きさでもくっきり描け、拡大縮小のアニメーションや発光ができる、という条件を満たすための構成です。

:::easy このページを読む前に
画面に文字を出すには、フォントのファイルに入っている「形の線」を、ピクセルの絵にする必要があります([[freetype]])。さらに、文字を正しい順番と間隔で並べる必要があります([[harfbuzz]])。

ame-shell は、文字の絵を「縁からの距離」の形([[sdf|距離場]])で作っておきます。そうすると、文字を大きくしても小さくしても、作り直さずにくっきり描けます。UI はばねで拡大縮小するので、これが大事です。
:::

## なぜ SDF(距離場)にするか {#sdf}

```zig
// SDF にする理由: 1つのアトラスから任意サイズで滑らかに描け、拡大縮小アニメーションや
// 発光(グロー)をシェーダの閾値操作だけで作れるため。全サーフェスで共有する。
pub const BASE_PX: f32 = 40; // SDF を生成する基準サイズ(大きいほど高品質だが生成が遅くアトラスを食う)
const SPREAD: c_int = 6;     // SDF の広がり(px)。グローの最大幅にもなる
```

普通の文字の描き方(大きさごとにビットマップを作る)だと、**大きさが変わるたびに作り直し**が必要です。ame-shell の UI はばねで拡大縮小する(ドロワーが開く・OSD がポップする・歌詞が弾む)ので、毎フレーム違う大きさになります。

SDF は「各ピクセルが文字の輪郭からどれだけ離れているか」を記録した画像です。**基準の 40 px で 1 回だけ作れば**、どの大きさでもシェーダの中で輪郭を計算し直せます。

```glsl
} else if (kind == 3.0 || kind == 7.0) {     // SDF 文字(7 は縦)
  float v = texture(u_atlas, v_uv).r;
  float k = v_p0.z;           // 基準px → 画面px の倍率
  float dist = (v - 0.5) * 2.0 * 6.0 * k + 0.15;  // 画面px単位の符号付き距離(内側が正)
  float a = clamp(dist + 0.5, 0.0, 1.0);
  vec4 col = pm(v_c0) * a;
  if (v_p0.w > 0.0) {         // 発光
    float g = clamp(1.0 + dist / v_p0.w, 0.0, 1.0);
    col += pm(v_c2) * g * g * (1.0 - a);
  }
  o = col;
}
```

- アトラスの値 0.5 が輪郭、±0.5 が ±6 px(SPREAD)。これに「基準 → 画面」の倍率 `k` を掛けて、**画面のピクセル単位の距離**に直してから、1 ピクセル幅でなめらかにします。拡大しても縮小しても輪郭の幅は常に 1 物理ピクセルです。
- `+ 0.15` は、ほんのわずかに太らせる補正です。SDF の文字は小さいサイズで細く見えがちなためです。
- **発光(glow)は同じ距離から作ります**。輪郭の外側に向かって距離に応じて弱くなる光を、追加のぼかし処理なしで描けます(大きな時計・ロック画面の時計の光)。
- **縦書き**(種類 7)は、UV を 90° 回して読むだけです。縦バーのウィンドウ名に使っています。

| 方法 | 大きさの変化 | 発光 | 判断 |
|---|---|---|---|
| **SDF のアトラス** | 1 回作れば全部の大きさ | 距離から計算 | ✓ 採用 |
| 大きさごとのビットマップ | 大きさのたびに作る。アニメーション中は毎フレーム | 別にぼかしが必要 | 拡大縮小と相性が悪い |
| 輪郭(ベクター)を GPU で直接塗る | どの大きさも最高品質 | 別処理 | 実装が大きい。日本語のグリフ数では割に合わない |

## 輪郭から直接ではなく「画像 → SDF」 {#bsdf}

```zig
// アウトラインから直接 SDF を作る("sdf" ラスタライザ)と CJK で 1 字 6ms 以上かかるため、
// まず通常のアンチエイリアス描画をしてから、そのビットマップを SDF に変換する("bsdf")。
if (c.FT_Render_Glyph(slot, c.FT_RENDER_MODE_NORMAL) != 0) return null;
_ = c.FT_Render_Glyph(slot, c.FT_RENDER_MODE_SDF); // 失敗時(カラー絵文字等)は通常のビットマップのまま
```

FreeType には SDF を作る方法が 2 つあります。輪郭から直接作る `sdf` は正確ですが、画数の多い漢字では**1 字 6.6 ms**かかりました。ランチャーを初めて開いたとき、約 100 字が一度に必要になり、**1 フレームが 525 ms** になっていました。

いったん普通のアンチエイリアスで画像にしてから SDF に変換する `bsdf` に変えると、**1 字 2.2 ms**になりました。UI の文字の大きさでは、品質の差はスクリーンショットを並べても見分けられませんでした。さらに[アイドル時間の先読み](#/tech-loop)と組み合わせて、**開いたときに作るグリフは 0 字**になっています。

- `FT_LOAD_NO_HINTING`: ヒンティング(小さい文字をピクセルの格子に合わせる処理)は特定の大きさ向けなので、どの大きさにも使う SDF では切ります。
- カラー絵文字は SDF にできないので、普通のビットマップのまま置きます。

## 書体を選ぶ: 足りない字は fontconfig に聞く {#fallback}

```zig
pub fn faceFor(self: *Fonts, chain: u1, cp: u32) u16 {
    const key = (@as(u64, chain) << 32) | cp;
    if (self.cp_face.get(key)) |f| return f;          // 「この字はどの書体で」をキャッシュ
    … チェーンの書体を順に試す …
    if (found == null and cp > 0x20) {
        // その文字を含むフォントを探す(絵文字や記号など)
        … FcCharSetAddChar(cs, cp) で fontconfig に問い合わせ …
        // 見つかった書体をチェーンに足す(次からは問い合わせない)
    }
    …
}
```

1. まず UI の書体(既定は **Noto Sans CJK JP**)、次にアイコン用の Nerd Font。
2. それでも無い字(絵文字・珍しい記号)は、fontconfig に「この文字を含む書体」を聞き、見つかったらチェーンの後ろに足します。
3. 「この文字はどの書体」を**ハッシュ表にキャッシュ**するので、問い合わせは文字ごとに 1 回だけです。

**書体の名前を明示している理由**: 作者の環境では `fc-match sans:lang=ja` が**韓国語の書体(KR)**を返しました。漢字の字形が日本語と違って見えるため、`Noto Sans CJK JP` を名前で指定しています。

## 並べる: HarfBuzz {#shape}

```zig
// 同じ顔で描ける区間(ラン)ごとに HarfBuzz に渡す。
c.hb_buffer_add_utf8(self.hb_buf, str.ptr, @intCast(str.len), @intCast(run_start), @intCast(i - run_start));
c.hb_buffer_guess_segment_properties(self.hb_buf);
c.hb_shape(face.hb, self.hb_buf, null, 0);
```

- 文字列を「同じ書体で描ける区間(ラン)」に分け、ランごとに HarfBuzz で並べます。カーニング・合字・結合文字(濁点の結合など)・アラビア文字の形の変化まで、HarfBuzz が正しく処理します。
- `hb_buffer_add_utf8` には**文字列全体と区間**を渡します。区間だけを渡すと、前後の文字を見る処理(文脈による形の変化)が正しく働かないためです。
- 結果のグリフごとに `cluster`(元の文字列のバイト位置)を残し、**折り返しの位置**の計算に使います([このサイトの歌詞の折り返しの修正](#/tech-site)もこの値を使っています)。

## アトラス: 最初から 2048² {#atlas}

```zig
// アトラスは 2048²(GPU 側に確保され、CPU の常駐メモリはほぼ増えない)。
// 途中で拡張するとキャッシュ全消去 → 全グリフ再生成のスパイクになるため、最初から最大で確保する。
const ATLAS_MIN: c_int = 2048;
const ATLAS_MAX: c_int = 2048;
```

- 1 チャンネル(`GL_R8`)の 2048 × 2048 = 4 MB を GPU に確保します。CPU 側にコピーを持たないので、常駐メモリはほぼ増えません(計測で確認)。
- 以前は小さく始めて足りなくなったら広げていましたが、広げるときに**全部のグリフを作り直す**ので、その瞬間に大きなスパイクが出ました。最初から最大にしてスパイクを無くしています。
- 初期化で 0 埋めのデータを CPU から送っていた分(+11 MB)を、GPU 上でのクリアに変えて減らしました。
- グリフの置き方は「行に左から詰め、はみ出したら次の行」の単純な方法です。UI で使う文字の数(数千字)なら十分です。

## まとめ: 得られた結果 {#result}

| 項目 | 結果 |
|---|---|
| 1 字の生成 | 6.6 ms → **2.2 ms**(bsdf) |
| ランチャーを初めて開く | 525 ms → **生成 0 字**(先読み) |
| 文字の拡大縮小・発光 | 追加の処理なし(シェーダの計算だけ) |
| 日本語・アイコン・絵文字の混在 | 自動のフォールバックで 1 行に並ぶ |
| メモリ | アトラスは GPU 側の 4 MB。全サーフェスで共有 |

## 研究者向けの補足 {#research}

:::research 距離場の文字の品質と限界
単一チャンネルの SDF は、輪郭の曲率が距離場の解像度(ame-shell は基準 40 px、広がり 6 px)に対して大きい部分、特に**鋭い角**で丸まります。これは、角の近くで「最も近い境界の点」が不連続に切り替わり、双線形補間した距離のゼロ等高線が角を切り取るためです。MSDF(Chlumský, 2015)は 3 チャンネルにそれぞれ別の辺の距離を持たせ、中央値でゼロ等高線を復元して角を保ちます。UI の大きさの日本語の字形では、角の丸まりは視認できませんでした(本文)。

`bsdf`(ビットマップ → 距離場)は、アンチエイリアスした画像の被覆率を境界の位置の手がかりとして、距離変換を行います。厳密なユークリッド距離変換は O(N) のアルゴリズムが知られていますが(Felzenszwalb と Huttenlocher, 2012)、FreeType の実装の詳細は本文で比較した測定(1 字 6.6 ms → 2.2 ms)で評価しています。

参考: C. Green, SIGGRAPH 2007 / V. Chlumský, 2015 / P. Felzenszwalb, D. Huttenlocher, Theory of Computing 8, 2012。
:::
