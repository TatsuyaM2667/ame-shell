# メモリが返ってこない: libc の mimalloc と、消されない GPU の同期オブジェクト

「メモリがめっちゃ使われるようになった」「すぐ固まる」。11 月の 9 日から 11 日にかけて、この 2 つを追いかけました。原因は 3 つあり、どれも ame-shell のコードの外にありました。

## 1. 返したメモリが返らない {#mimalloc}

ame-shell の私有メモリ(`Pss_Anon`)は 150〜280 MB。目標は 60 MB です。まず、何がメモリを持っているのかを知るために、Zig で小さなトレーサを書きました。`LD_PRELOAD` で malloc 一式を差し替え、呼び出し元(4 段)ごとに「今生きているバイト数」を数えて、起動から 12 秒後に上位を出すものです。

結果は「生きている確保は約 42 MB」。残りの 100 MB 以上は、もう free された分でした。

試しに 590 MB を確保して全部 free する小さなプログラムを動かすと、私有メモリは 590 MB のまま。`LazyFree`(あとで返す印)も 0 です。Chimera Linux の libc は musl に [[mimalloc]] を組み込んでいて、**解放したメモリを OS に返していなかった**のです。`mi_collect` も `malloc_trim` も出ていないので、外からは何もできません。

そこで、実行ファイルの中で malloc 一式を定義しました。ELF の決まりで、Mesa も mpv も FreeType もこちらを使います。16 KB 以上は `mmap` で直に取って `free` で返し、小さいものは libc に任せます。

最初の版は CPU が 1.6 倍になりました。原因は、見出しの 16 バイトのせいで大きいブロックの中身がページ境界から 16 バイトずれ、動画のコマの転送が遅い道に落ちていたことです。64 バイト境界にそろえると元に戻りました。

```text
動画壁紙のときの私有メモリ: 210 MB → 115 MB(CPU は同じ)
```

## 2. 1 コマに 3 個ずつ溜まる {#fence}

それでも、動画の壁紙のときは 1 分に約 1.3 MB ずつ増えていました。トレーサを「40 秒と 160 秒の 2 回出す」形に変え、増えた呼び出し元だけを並べると:

```text
+223KB n=4583 < libgallium < libgallium < libgallium < libmpv < libmpv
+223KB n=4582 < libgallium …
+167KB n=4583 < libgallium < libmpv < … < mpv_render_context_render
```

120 秒で 4,583 個、ちょうど 1 コマに 1 個ずつ、それが 3 か所。libmpv の呼び出し元を逆アセンブルすると、関数ポインタを呼ぶ直前に `mov $0x9117, %edi`。`0x9117` は `GL_SYNC_GPU_COMMANDS_COMPLETE`、つまり `glFenceSync` でした。libmpv 0.41 の描画 API は、**1 コマごとに GPU の[[gl-sync|同期オブジェクト]]を作って、消していませんでした**。

`mpv_render_context_report_swap` を呼んでも変わらず。`glFenceSync` を渡さないようにすると、今度は mpv が「OpenGL を初期化できない」と動画を諦めます。最後は、mpv が GL の関数を ame-shell の `get_proc_address` から受け取ることを使い、`glFenceSync` / `glDeleteSync` / `glClientWaitSync` を包みました。最近の 8 個だけを残して古いものは消し、消し済みのものを mpv が待つときは「もう終わっている」と答えます。

```text
2 回目のトレース: 65,483 KB → 65,475 KB(増えない)
```

## 3. 固まっていたのは機械全体 {#freeze}

「すぐ固まる」の方は、0.5 秒ごとに ame-shell に問い合わせ、遅いときにスレッドの状態を残す見張りを置いて捕まえました。固まった瞬間の記録は、空きメモリ **93 MB**、mpv のスレッドが `D` 状態(`folio_wait`、ページの読み直し待ち)。スワップの無い機械でメモリが尽き、OOM キラーが動く前にページの追い出しと読み直しを繰り返していました。

2 つの手を打ちました。

- **[[zram]]**: RAM の中に圧縮したスワップを作る `scripts/zram-setup.sh`(Chimera の dinit の `zram-device`)。
- **メモリの見張り**: カーネルの [[psi|PSI]](メモリ待ちの割合)の知らせを `EPOLLPRI` で待ち、空きが 10% を切ったら通知、3% を切ったらいちばんメモリを使っているプロセスを止めます。

見張りを入れた翌日、記録に `RDD Process(5903 MB)を止めました` が残っていました。ブラウザ(Zen)の動画の復号プロセスです。ハードウェアで復号したコマを GPU のバッファとして抱えたまま膨らみ、私有メモリの順位には出てこないので、それまでの記録では見えていませんでした。しかも最初の見張りは、カーネルと同じ `oom_score` で止めるものを選んでいたので、ブラウザが「先に止めてよい」印を付けた数 MB のタブばかりを止めていました。今は、実際に使っている量(常駐 + スワップ)で選びます。

## 振り返り {#lessons}

- **「返したはず」は測らないと分からない**。生きている確保の量と、プロセスの私有メモリの差が、そのまま「返っていない量」でした。
- **差を取る**。1 回の記録では大きい順に並べても犯人は見えず、2 回の差を取ると 1 行目に出ました。
- **見えないメモリがある**。GPU のバッファやドライバのオブジェクトは、私有メモリの順位に出てきません。記録の物差しは、見張りで実際に使う物差し(常駐 + スワップ)とそろえるべきでした。
